# 数值、Buff 与高频事件架构

状态：下一阶段实现设计。目的不是先做大量道具，而是让少量道具可靠地修改角色、物品与经济数据；场景重建、合成、换位、结算和存档后都能解释“这一点属性从哪里来”。本文细化 `06-技术架构.md`，当前 `PrototypeRun`、`PrototypeActor`、`PrototypeItemDefinition` 尚未按此重构。

## 1. 先划清四种状态

| 层 | 对象与示例 | 存储位置 | 何时清除 |
| --- | --- | --- | --- |
| 不可变定义 | 武器原始伤害、道具等级效果、Buff 叠加规则、商店权重 | ScriptableObject 内容资产，运行时只读 | 版本更新时迁移，不在战斗中改写 |
| 本局持久状态 | 玩家针剂、突破奖励、金币、已购道具、道具自身永久成长、出售次数 | `RunState`、`ItemInstance`、账本与存档 | 一局结束；存档读入后继续 |
| 战斗状态 | 当前生命、护盾、2 秒加速、冷却、触发次数、待结算矿石 | `CombatState` / `BuffRuntime` / `PendingLootLedger` | 战斗结束后按规则结算；临时 Buff 清除 |
| 表现状态 | 角色贴图、枪模型、伤害数字、UI 显示数值 | Unity GameObject、UI ViewModel、对象池 | 可随时重建，不是规则真相 |

“永久”必须声明作用域：`RunPermanentOnCharacter`（本局角色，卖出来源仍保留）、`RunPermanentOnItem`（道具实例，卖出主件后离开本局）、`WhileEquipped`（持有期间）、`ThisCombat`（本场）、`Timed`（持续若干模拟步）。不同作用域使用不同命令和存储，不允许用一个含糊的 `isPermanent` 布尔量代替。

### 数据身份

- 每件物品具有 `instanceId`，引用不可变 `definitionId`、等级、槽位 ID、已投入价格、实例成长修正列表和合成/突破来源。两件同名一级仍是两个不同实例。
- 每条修正具有 `modifierId` 或确定的来源键（例如 `item:123:socket:R1:effect:shield`）、来源实例 ID、目标 ID、属性 ID、操作类型、数值、作用域、叠加组、版本。相同来源重新计算时**替换/重建**，不得再 `+=` 一次。
- 每次交易、注射、合成、吞并、结算具有唯一 `commandId`；一次性的突破奖励另有稳定 `grantId`。账本记录已提交 ID，重放或界面重复提交时返回原结果。
- 规则金额使用整数；百分比在规则层可用定点数（例如万分比）或统一精度的数值表示，避免保存后因浮点累加漂移。物理速度仍可用 float，但规则入账不依赖渲染帧。

## 2. 一次修改怎样可靠生效

所有持久改变走命令服务，不允许 UI、装备贴图或碰撞脚本直接修改 `ScriptableObject`：

```text
UI/战斗触发 → Command（实例 ID、目标、参数、commandId）
             → 校验前置条件（金币、数量、格位、等级、上限、阶段）
             → 在同一事务中写入 RunState/ItemInstance/账本
             → 提交状态版本号 stateVersion
             → 标记受影响属性与关系拓扑 dirty
             → 发布一次 StateChanged（只读快照）
             → UI/表现层刷新
```

例如购买并注射生命针剂是两个命令。购买扣金币并加入针剂实例；拖到角色时先算预览，松开后在一个事务内扣针剂数量、追加 `+10 最大生命` 的角色本局修正和注射记录，再更新数值快照。若中途失败，三个写入都不发生。吞并同理：移除副件、给主件写成长、更新库存索引必须一起提交。合成既要保留主件成长，也要明确副件实例成长是按规则迁入、折现还是丢弃；UI 先展示结果，内容定义写 `MergePolicy`，不能隐式处理。

持久状态在准备页交易后保存检查点，战斗结算完成后再保存检查点。存档采用版本化 DTO、稳定定义 ID、临时文件写入并安全替换；读取时验证定义存在、命令账本没有重复 ID、物品实例无重复、金钱非负、格位 ID 合法。战斗中途存档若后续要支持，需连同模拟步号、Buff 剩余时间、冷却、待结算账本与事件队列一并保存；第一阶段只支持准备/结算边界存档，并在 UI 明示。**场景或 UI 重建绝不能新建 `RunState`，否则看起来就是 Buff/成长丢失。**

## 3. 统一属性计算器

`StatManager` 维护 `StatSnapshot`：生命上限、速度数值、目标速度、质量、体型、近/远程基础伤害、撞击加成、承伤倍率、能量消耗、经济修正等。所有效果都生成 `StatModifier`，由计算器按确定的顺序聚合：

1. 角色基础属性与道具等级基础值；
2. 本局永久固定值（针剂、突破奖励）和道具实例永久固定值；
3. 持有期间固定值（装备、格位、位置协同）；
4. 本局永久与持有期间的同组百分比加成；
5. 本场 Buff 的固定值与同组百分比；
6. 明确允许的独立乘法组，最后施加软/硬上限，再算质量和目标移动速度。

同组百分比先相加，例如两个 `+10% 武器伤害` 得 `+20%`，不是 `1.1×1.1`；独立乘法组很少开放，并在内容表标注。计算器返回每项属性的 `StatBreakdown[]`，UI 可以列出来源、原始修正、因上限被截断的量。初始值与 `ItemDefinition` 不随战斗永久改写；临时 Buff 结束只是从活动集合移除并重算快照，旧值不会“减回去”而产生漂移。装备换位时重新构造位置修正集合，而非累积加减。

属性快照有 `stateVersion`。购买、注射、合成、换位使对应属性 dirty；同一命令链提交后按需重算一次。战斗中 Buff 增减时在**同一固定模拟步的下一个相关属性读取之前**更新受影响属性；不必每帧重算所有属性。UI 可以 10Hz 刷新显示，但规则快照必须实时正确。当前生命不会因生命上限上升而自动按比例治疗，除非效果明说；当前生命只需 clamp 到新上限。最大生命影响有效质量，质量与速度在这次提交后同步重算。

## 4. Buff 管理器

`BuffDefinition`（静态）声明效果列表、作用属性、持续类型、叠加策略、最大层数、触发间隔和视觉 ID。`BuffRuntime`（动态）保存 `buffInstanceId`、来源道具/事件、目标、层数、强度、开始步号、到期步号、下次 tick 步号、已触发次数。只有 `CombatState.BuffManager` 是本场 Buff 的权威拥有者；UI 图标和角色光效从其只读快照创建。

| 策略 | 例子 | 行为 |
| --- | --- | --- |
| `ReplaceIfStronger` | 护盾增伤光环 | 保留较强来源，到期后可回落到仍有效的较弱来源 |
| `RefreshDuration` | 轮胎命中加速 | 同来源只刷新到期步号，不增加层数 |
| `AddStacks` | 每次受击 +1 层防护 | 达到上限后不再增加；失效一次移除整组或按定义逐层衰减 |
| `IndependentBySource` | 两件不同盾牌 | 不同来源分别计时，卸下其中一件只清它的 Buff |
| `UniquePerTarget` | 只能有一个灼烧状态 | 按统一规则选择强度和剩余时间，不受回调顺序影响 |

Buff 的增减进入 `BuffCommand`，使用来源键去重。到期由按步号排序的小顶堆/时间轮处理，不要求每个 Buff 挂一个 MonoBehaviour `Update()`。`OnApply/OnStack/OnExpire` 只产生结构化效果命令；内容校验阻止互相无界触发。卸下道具时仅清理“持有期间”来源的 Buff；已提交的角色本局永久成长继续存在。战斗结束清除 `ThisCombat/Timed`，只将明确标为本局永久且已提交的成长保留。角色死亡不自动清除 Buff，死亡结算需要明确选择哪些“死亡时触发”还能执行。

## 5. 战斗事件的时序与延迟预算

Unity 物理仍用固定模拟步（目前可取 `Time.fixedDeltaTime = 0.02s`）；**0.2～0.25 秒不是统一游戏帧**，只可作为某些道具的触发冷却、伤害数字合并窗口或经济产出统计窗口。伤害、减伤、生命变更、死亡、即时 Buff 必须在产生它们的固定模拟步中完成，不能等待窗口关闭。

建议同一固定步的顺序：

```text
收集物理接触/武器到期（紧凑结构体）
→ 归并同一接触对与重复命中 ID
→ 固定顺序执行 PreHit（护盾/闪避）
→ 计算伤害和减伤，并立即写生命/护盾
→ 执行 OnHit/OnDamaged 的 Buff 与道具触发
→ 处理这些触发新产生的事件（广度优先、同一固定步）
→ 处理死亡/胜负候选与待结算账本
→ 发布本步只读快照和表现事件
```

时序定义要固定：`OnHit` 增伤默认影响**下一次**命中；若道具想影响当前伤害，必须声明 `PreHit`。同时命中的两方先形成同一批接触，再按事件 ID 排序结算，避免 MonoBehaviour 回调顺序改变结果。事件包含 `eventId`、`step`、`sourceInstanceId`、`targetId`、`kind`、`chainDepth`、`originEventId`、`rngSequence`。固定种子和固定顺序让战斗可复现、可追查。

以高频命中产矿为例：同一命中只记一次，计数器即时从 1 变 2，当步立即写 `PendingLootLedger` 的矿石数量；画面可在下一渲染帧汇总显示“+1 矿”，但库存不用等 0.2 秒。战斗结束把待结算记录通过带 `battleId` 的一次性结算命令转为临时领取区，避免重复发奖。

### 负载控制的优先级

1. **内容层抑制无界事件**：触发器声明每秒次数、每场次数、连锁深度、来源/目标保护窗；生成同类资源有每场上限。对“触发另一个触发器”建立图关系，编辑器标出自循环或无上限闭环。
2. **规则层批量处理**：接触、伤害和 Buff 命令使用可复用数组/环形队列及结构体，按模拟步批量读取，不为每条事件新建 GameObject、闭包或 LINQ 枚举。属性 dirty 集合允许本步多次添加、只重算一次无依赖冲突的项。
3. **表现层降级**：伤害数字在 0.1～0.2 秒内按目标/类型合并；粒子与音效对象池有可见预算，超预算就简化或跳过表现。**真实伤害、Buff、永久成长和资源入账不能被表现预算丢弃。**
4. **测量后优化**：Unity Profiler、GC Alloc、每步事件数和最慢步耗时决定是否把纯数据部分迁到 Jobs/Burst。Unity 物理对象和 UGUI 仍由主线程管理，不能仅因为“并发很多”就跨线程写 `Rigidbody` 或资产。

为避免单步无限递归，对效果链设置深度和次数硬上限。达到上限时停止**新派生的可选触发链**，记录明确的 `TriggerBudgetExceeded` 和来源道具，绝不把已算出的生命/资源修改静默延迟到下一步，也不吞掉原始命中。优先通过配置验证与限频让正常内容永远碰不到硬上限；压力测试故意构造闭环验证保护行为。

## 6. 持久增长与并发交易的边界

局内永久成长（例如矿镐三级突破给角色 +2% 近战伤害）只经 `GrantRunModifier` 命令，使用稳定 `grantId = battle/run + sourceInstanceId + effectId + occurrence`。即使战斗事件重复派发、结果页重开或读档重放，相同 `grantId` 只能提交一次。道具实例永久成长（如齿轮吞并）更新实例成长账本，合成迁移由明确 `MergePolicy` 执行。金币、矿石、针剂均通过一套资源账本入账，并保留来源；商店不会直接读写 `PrototypeRun.Gold` 字段。

物理回调只向本固定步收集队列追加事件；准备阶段交易只在主线程事务入口执行。未来 Jobs/Burst 只处理已经复制出来的纯数据快照，再由主线程按确定顺序提交结果。无需为每次攻击创建线程，也不要让多个处理器同时修改同一个角色数值。这里的主要难题是**高频事件的正确顺序和可复现性**，不是线程数不足。

## 7. 从当前原型迁移的步骤

1. 建立 `ItemInstance`、`RunState`、稳定 ID 与保存 DTO；从现有 `PrototypeItemDefinition[] Bag/Equipped` 迁移成实例集合，保留现有购买、装备和 4→6→8→10 格行为。
2. 把 `PrototypeRun.GetStats` 改成 `StatManager.CalculateSnapshot`；UI 与 `PrototypeActor.Initialize` 都读同一快照。先做生命、速度、撞击加成、撞击减伤四个属性的来源明细。
3. 加入 `GrantRunModifier` 与针剂消耗命令；做保存/重载与场景重建实验，确保角色本局永久加成保持，卸装备时位置被动正确消失。
4. 实现 `BuffManager` 的 2 秒加速、开战护盾、命中叠层三种样例；测试同来源刷新、不同来源并存、到期、死亡、再战清空。
5. 将碰撞和攻击回调改为事件收集与固定步结算，接入矿镐待结算账本和商店吞并交易。最后做对象池及压力场景，先记录基线再考虑 Jobs/Burst。

## 8. 必须自动验证的性质

- 1+1→2、2+2→3 后实例 ID、来源、实例成长和槽位正确；四件一级的花费与出售价值可追踪；错误合成不消耗任一件。
- 装备、卸下、换位、扩格重复一百次后属性回到相同数值；不会多加或少减。相邻/对位关系变化仅影响对应来源。
- 注射、突破、吞并、结算在同一个 `commandId/grantId/battleId` 被重放两次时只生效一次；保存后重读结果相同。
- 2 秒 Buff 在指定模拟步到期；同来源刷新不重复叠层；战斗结束清掉临时状态，本局永久属性继续存在。
- 同一固定种子、装备、发射向量运行多次，伤害账本和胜负一致；高频场景不丢实际伤害或矿石。
- 压力场景目标先沿用 `06-技术架构.md`：每秒 2000 条逻辑事件、100 个投射物表现，记录主线程毫秒与每帧 GC；在真实设备实测后确定正式预算。若超标先定位热点和无界触发，再改数据结构或并行计算。
