# 架构审查与基础治理

第二轮实现已完成，当前进度见 [40-状态边界与统一战斗调度](40-状态边界与统一战斗调度.md)。下文保留首轮审查时的发现：阶段约束、只读容器、战斗 ID、统一推进和持续飞剑分离已有后续修复，属性来源部分收口；未完成项以 40 的末节为准。

本次基于源码、配置与原项目 Unity 2022.3.62f3c1 的后台回归。结论：项目已有可运行的玩法与部分数据驱动基础，但 `06`、`13` 中的目标架构并未完整落实；`33`、`37`、`38` 的部分实现声明也有具体缺口。当前适合继续渐进整理，不宜直接把原型称为完整的可扩展战斗框架。

本报告覆盖运行状态、战斗调度、属性/Buff、物品成长、存档、主播模式、表现配置和模块边界。没有把历史文档中的测试次数作为本次通过的证据；没有完成逐道具连续录像、长期平衡或目标设备 Profiler 验收。

## 1. 优先级结论

### P1：统一战斗步的权威入口尚未形成（部分修复，仍需优先推进）

证据：`PrototypeBattle.FixedUpdate/ResolveActorCollision`、`PrototypeActor.FixedUpdate/CombatTick/OnCollisionEnter`、`PrototypeProjectile.FixedUpdate`。

Battle 依次处理双方状态、装备释放、延迟命中和胜负；Actor 自己处理运动与能量耗尽伤害；碰撞回调直接结算撞击；持续飞剑又在自己的 FixedUpdate 中提交伤害。没有 `eventId/step/originEventId` 的统一事件批次，没有独立战斗 RNG。暴击使用全局 `UnityEngine.Random.value`，本局随机使用未保存状态的 `System.Random`。因此不能保证仅凭装备和发射参数重现同一事件序列，不能把固定帧率等同于确定性。

具体已修复：普通弹体原来在 96 个显示对象耗尽时退化为按初始距离计算的定时命中，正常路径则追踪移动目标且在发射者死亡时取消。两条路径的规则不一致。现在普通弹体全部由同一个逻辑队列和 `PrototypeProjectileFlight` 推进，显示对象可缺席；反应新产生的普通弹体在下一次队列推进处理。双方临时 Buff 的到期统一放在双方 CombatTick 之前；原来在各 Actor 的 FixedUpdate 中到期，读取结果依赖组件执行顺序。

剩余工作：将运动/耗能、碰撞收集和持续飞剑也归入显式阶段；再统一延迟攻击、反应链、死亡与胜负结算。不建议仅用 Script Execution Order 掩盖跨组件依赖。Unity 物理的跨平台逐位确定性不是本次承诺；先建立同环境下可追踪的事件顺序与随机序列。

### P1：准备阶段操作缺少统一的阶段和幂等边界（未修复）

证据：`PrototypeRun.Buy/BuyToSlot/Equip/MergeBag/Sell/MoveEquipped/SellEquipped` 没有统一检查 `combatActive`；只有 `UseInjection/Expand/Park` 等少数入口检查。`Bag/Equipped/PermanentModifiers` 虽声明 readonly，但集合内容和实例字段仍可被外部修改。

场景 UI 隐藏通常限制了玩家入口，但公共规则 API 仍允许战斗中卖掉或换掉装备。Actor 保存了装备实例引用，可能继续使用已经离开背包的物品；未来快捷键、编辑器或其他页面接入容易绕过 UI 约束。`StartCombat` 重复调用还会重新清空待结算数据。没有持久化 commandId/grantId 账本；`CommitCombat` 只有当前对象内的布尔保护，不能据此称为通用幂等事务。

建议先引入 Prepare/Aiming/Fighting/Resolving/Ended 的应用状态，所有交易入口集中做阶段校验，使用稳定实例 ID 参数和结构化结果；再把购买/合成/吞并/结算迁到命令服务。验收必须覆盖战斗中调用全部交易 API 被拒绝、同一命令重复提交不二次扣款、失败合成不改变任何容器。不能只测试按钮是否隐藏。

### P1：存档身份与失败恢复不足（本次加固，仍未完全事务化）

证据：`PrototypeRun.Persistence.cs` 的 `TryLoad`。原实现先清空现有容器再逐项载入；缺失定义被静默跳过，重复实例 ID 不拒绝，nextId 没有保证大于已有 ID。

本次改为先构造三组待载入物品并校验跨容器唯一 ID、未知定义、无效 ID、ID 溢出与容器长度，再修改当前库存；nextId 修复为大于所有已加载 ID。保留 Unity 将空槽反序列化为空对象的兼容。启动读盘拒绝存档时，在任何新检查点覆盖前保存 `.rejected-<guid>.json` 原文；备份失败则抛出 IO 错误，阻止继续覆盖。存档版本仍为 7，未变更 DTO 格式。

边界：这还不是完整的 RunState 候选对象原子替换。自定义怪物、浮点数、配方/继承程序深层内容仍需统一验证；恢复战斗会调用 CommitCombat，这个载入副作用应在下一步显式化。异步保存错误主要在 Flush 才抛出，尚无 UI 可见的保存失败状态。现在能拒绝坏物品且保留原文，但没有实现完整恢复界面。

`24` 已明确中断时结算已记录产物与成长、不恢复整场战斗、不自动计胜场。此行为属于后续接受的设计，不能仅按 `13` 的早期边界存档建议判定为错误；仍需要中断恢复与重复结算专项测试。

### P1：词条稳定身份没有完全写入内容（本次修复已有内容）

扫描 73 个唯一道具，发现 25 条旧词条没有显式 id。`PrototypeModifierLedger.EnsureEffectIds/EffectKey` 会用索引和类型生成身份；运行时暂时可用，但调整原 JSON 的词条顺序再读旧档，会改变历史成长对应的键。与 `33` 所述“稳定词条 ID”并不完全一致。

已在 JSON 及对应后备 ScriptableObject 资产中写入这 25 条词条原本使用的 `effect:<原索引>:<原类型>` 值。使用旧键是为了保留现有账本，不是继续把索引作为新身份生成规则。之后调序必须保留该字段；新词条应创建新 ID。回归检查同时检查 JSON 和后备资产，验证旧账本键与重排后的查找。运行时对外部旧配置的兼容生成逻辑仍保留。

### P1：持续飞剑仍把显示合批当作战斗实例合并（未修复）

证据：`PrototypeBattle.Projectiles.ReleaseFlyingSword`、`PrototypeProjectile.MergeSword/Rally/FixedUpdate`。每方 16 个实体满后把新剑 payload 的 damage/poison/burn 叠加到旧剑，沿用旧剑位置、飞行阶段和节奏；新增剑还会 Rally 全部已有剑。

这不是单纯减少显示对象：新剑的独立路径和命中时刻被改变，护盾破裂等中间反应也可能从多次命中变成一次。不能用总伤害相加直接证明等价。需要先明确“新增剑是否让所有剑重新出击”的玩法规则，再做独立 SwordRuntime + 可合批 SwordView。验收覆盖 15/16/17/32 剑的逐次命中、护盾破裂与新增召唤时序，而不是只检查累计数值。

### P2：Buff 和属性系统只能支持现有子集（未修复）

证据：`PrototypeBuffManager`、`PrototypeStats`、`PrototypeActor.ApplyStat/AddBattleHealth/GrantInvulnerability`。

- 普通 Buff 支持按 source+stat 刷新、线性累计和按步到期；没有 BuffDefinition、最大层数、完整叠加策略、来源移除和只读快照。
- 盾/毒/火/再生按类型汇总在数组中，无法知道哪件道具贡献多少，也无法按来源驱散。`33` 明确采用类型聚合，因此这属于当前能力边界；若采用 `13` 的来源型通用 Buff 目标才需要升级。
- 无敌单独保存在 Actor 的 invulnerableUntil；部分配方直接改 SpeedStat、damageBonus、damageReduction，未进入 Buff 来源账本。UI 无法统一解释所有临时增量。
- 本局快照、Actor 运行数值和主播属性构造是三处计算路径。主模式使用 EffectMultiplier，主播构造部分字段使用 LevelMultiplier；这不必然是 bug，但不应声称所有数值计算共用同一条流水线。
- 修正记录只有 amount/scope，缺少明确 Add/Percent/MultiplyGroup 操作；减伤在 switch 中单独乘算。质量采用初始化快照，成长最大生命不会同步更新 massSnapshot，和 `13` 中动态同步质量的目标存在差异，需要结合后续史莱姆规则明确采用哪种语义。

建议先定义四种明确作用域：角色本局、物品实例、装备持有、本场/定时；把现有效果映射到统一 StatContribution 与 StatSnapshot，再补来源追踪、到期和叠加策略。不要一开始把 15 种效果全部做成任意脚本插件。

### P2：特效可调参数已经有了，组合扩展能力仍有限（部分修复）

证据：`PrototypeItemAnimation`、`PrototypeCombatPresentation.ShowActivation/Animate/AnimateConfigured`、`PrototypeActor.ExecuteProgram`。

73 件道具实际使用 15 种非 Auto/None 动画预设，具有颜色、尺寸、时长、数量、强度、图标、旋转覆盖。这可以支持“同一形态的不同参数”，不能等同于 73 套独立动画或自由组合的效果图。

本次修复真实配置失效：Crescent/Growth 原先额外判断死神/史莱姆 itemId，其他装备选择这两个预设落入通用默认表现。现在按预设进入月牙/成长渲染；回归验证普通矛也可选择，None 不生成装饰，动画选择不造成伤害。

剩余限制：

1. 效果执行使用大型 switch，吸收、矿镐、持续剑、史莱姆等仍按 itemId 分支；新增机制需要改 Actor。
2. 逻辑层直接调用 Presentation 与音效资源解析，没有只读 CombatPresentationEvent 边界。
3. 装饰池有 32 个槽，但切换 modelPrefab 时仍 Destroy/Instantiate，并非所有模型都已经对象池化。
4. 持续状态外观按硬编码类型、颜色和资源路径驱动，没有独立 StatusVisualDefinition。
5. 预设仍是固定函数，不能分别配置起手、飞行、命中、结束的多段组合。

建议按阶段建立表现定义（Release/Flight/Hit/Expire），以 renderer 注册表选择已有实现，让资源配置引用定义；战斗只发事件。保留 None 与 Auto 的现有兼容语义，所有样式参数只改变显示，不能改变次数和伤害。先迁移两个代表样例后再批量迁移。

### P2：依赖边界、验证资产和文档存在积债（部分整理）

运行脚本基本集中在 Combat/UI/Audio；Run 管经济、背包、天数、掉落、成长、存档，Battle 管场景搭建、镜头、UI、战斗和结算。Combat 引用 PrototypeUiSkin 等 UI 资源，无法直接按文档加入 Gameplay/Presentation/UI asmdef 而不先解决循环依赖。

本次将持久化实现拆为 `PrototypeRun.Persistence.cs`，将弹体管理拆为 `PrototypeBattle.Projectiles.cs`，新增不依赖 GameObject 的普通弹体运动状态。这是定位职责与后续抽服务的过渡，partial 并没有创造独立的服务边界，也没有解决所有大类问题。

此前 `33/38` 验证记录明确说临时测试已删除，难以复现。现在保留 Unity 编辑器回归入口与内容检查脚本。当前目录没有 Git 仓库；不能提供可信的 Git 基线 diff 或回滚提交。后续应把 Assets、Packages、ProjectSettings、Docs、Tools 与 .meta 纳入版本控制，排除生成目录。

## 2. 目前实际有哪些状态

| 状态层 | 当前拥有者 | 内容/生命周期 | 主要边界问题 |
|---|---|---|---|
| 静态定义 | Repository + ScriptableObject/JSON | 属性、标签、效果、动画；跨局复用 | All/定义仍可写；旧 ID 兼容逻辑会写定义 |
| 本局进度 | PrototypeRun | 天数、六段 DayStage、金币、等级、生命、精力、胜场、商店、掉落 | 与服务、UI文案、序列化混合 |
| 物品持久状态 | ItemInstance/ModifierLedger | 实例 ID、等级、成长、配方、吞并程序、冷却强化 | 大量 public 可写字段；缺通用事务约束 |
| 下一场状态 | PendingBattleModifiers | 准备阶段药水，StartCombat 清除 | 需独立验证重复开战/中断恢复消费语义 |
| 本场收益 | Run 内 combatProducts/Gold/Ore/Grants | 检查点、结算提交 | 与普通持久状态交织；无 battleId 账本 |
| 角色即时状态 | Actor + CombatState | 当前血/能量/速度、无敌、盾毒火再生 | 分散字段，并非一个 CombatState 权威快照 |
| 物品本场状态 | Actor.RuntimeItem | 冷却、生产计时、触发间隔、轮询游标 | 与执行器/表现耦合 |
| 临时属性 Buff | BuffManager | 来源刷新、累计、到期 | 非完整叠加策略体系 |
| 运动与攻击 | Rigidbody、Scheduler、普通弹体逻辑、持续剑 MonoBehaviour | 运动、延迟命中、在途快照、持续剑 | 统一调度尚未完成 |
| 应用/页面状态 | SceneSession/BroadcastSession/Battle/UI | 主菜单、准备、瞄准、开战、结果、主播草稿 | 多个布尔和静态会话共同决定状态 |
| 表现状态 | Presentation/UI/Audio 池 | 飘字、动画、图标、音效 | 普通装饰已独立；持续剑仍拥有逻辑 |

当前六个 DayStage 是 EventOne、EventTwo、Monster、EventThree、EventFour、Rival。它们描述一天的流程，不等同于 Prepare/Aiming/Fighting/Resolving 这类应用状态。后续应把两者分开建模。

## 4. 分阶段优化方案与退出标准

| 顺序 | 交付内容 | 完成标准 |
|---|---|---|
| 本次基础批次 | 普通弹体逻辑/显示分离、Buff到期入口、存档预校验/备份、25条稳定ID、预设修复、职责文件与回归入口 | 原版 Unity 编译；新增回归与内容扫描通过 |
| 下一批：规则边界 | 应用状态 + 交易命令入口；只读对外集合；开战/结算的 battleId | 战斗中无法交易；重复开战/结算不重置收益或重复奖励 |
| 下一批：调度 | CombatClock/整数 step、接触队列、统一攻击和死亡顺序、独立 RNG；迁移持续剑 | 同输入事件账本一致；15/16/17/32剑逻辑一致；关闭表现不改变结果 |
| 再下一批：数值/效果 | 单一属性计算入口、来源/作用域、EffectExecutor、共享校验；准备/主播用相同初始快照构造 | 卸装/换位100次可逆；升级不放大历史增量；临时状态全部正确清除 |
| 然后：表现与程序集 | 表现事件、独立资源解析、预设渲染注册表、按依赖拆 asmdef | Gameplay 不引用 UI/音效/Prefab；替换皮肤无需改规则；样式验收可复现 |
| 最后：性能治理 | Profiler基线、分配统计、逻辑/表现预算计数、压力场景 | 在声明的机器和配置下验证60FPS/GC/最慢步；依据热点决定优化 |

目标依赖是 UI/Presentation → Application → Domain，Unity 物理与存储作为适配器接入。先建立接口与只读事件，再移动目录或加 asmdef。仅移动文件不算架构完成；也不建议现阶段引入 ECS/Jobs 来解决状态所有权问题。
